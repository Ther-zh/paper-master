# 三类账本（Ledgers）：机制注册表 · 术语账本 · 设计-实现差异台账

> **v3.2 新增**。来源：论文重修事件复盘（Slow/Meta 被压成一段、保护区凭空出现、
> revision_rounds 从未接线）＋ math-modeling-agent `method_registry` / `terminology` 范式。
>
> **定位（轻机制）**：账本是 W1 的**可追踪产物**、W2 的**写作依据**、W5 的**审计对象**；
> 不做代码级自动验证——深核代码语义按需外挂（如 experiment-audit / evidence freeze）。
>
> **Born-Correct 原则**：账本在 W1 生成、W2 执行、W5 只做抽查。不在 W5 现补账本。

---

## 1. 机制注册表（Mechanism Registry）

**用途**：防止"看起来小"的模块在初稿被误判为不重要而漏写/压成一句（Slow/Meta 教训）；
防止"设计里写了、代码没接"的机制被默认写成已实现（revision_rounds 教训）。

**生成时点**：W1，叙事策略卡之后、Claims-Evidence Matrix 之前（claim 要回指机制）。

**来源（逐条枚举，不漏项）**：
- 代码：文件 / 函数 / 关键配置项（每条给锚点）
- 实验证据：消融表、日志字段、结果文件
- narrative / 设计文档：机制意图与状态

> **论文类型适配**：系统/方法型 = 模块/机制注册表；理论型 = 定理/引理/假设注册表；
> 实证型 = 实验/协议注册表。表列语义按类型换算（"触发与落点"→"假设与量词"等）。

**表模板**：

| 机制 | 档位 | 一句话定义 | 触发与落点 | 输入 → 产物与作用域 | 关键参数/判据 | 实现状态 + 锚点 | 证据 | 消融角色 | claim 贡献 |
|------|------|-----------|------------|--------------------|--------------|----------------|------|---------|-----------|
| | core / supporting / baseline | ≤1 句 | 何时生效、作用在哪个对象/字段/角色 | 吃什么 → 产出什么 → 影响范围 | 可调参数、阈值、判据数 | 已接入/部分/未接入/仅设计 + file:line | 结果文件/消融/日志 | 被拆/被替换/未验证 | 支撑哪些 claim |

**档位与展开强度**：

| 档位 | 判定信号（任一） | 展开强度（W2 执行） |
|------|------------------|---------------------|
| **core** | 主 claim 依赖 / 消融中被单独拆解 / 参数与判据 ≥3 项 / 分支多 / 首创机制 | 按**六槽展开卡**在正文逐槽写，独立小节或小节内完整段 |
| **supporting** | 为 core 服务但非论点本身 | 一段或一句，可合并 |
| **baseline** | 对照物 | 对比表内一句（合法简写） |

**重要性信号（防首轮低估）**：判据数 / 分支数 / 自由参数数（如 λ）/ 消融是否单独拆解 /
主 claim 是否依赖。**不要用代码行数当代理**——小代码多判据的机制（Slow 四类判据）恰恰最需要展开。

**六槽展开卡（core 机制在 W2 逐槽回答）**：

1. **动机**：为什么需要它（现有方案为什么不够）
2. **定义**：是什么（用词以术语账本为准）
3. **触发与落点**：何时/何处生效（写进哪个字段、注入哪个角色）
4. **输入 → 产物与作用域**：吃什么、产出什么、影响范围
5. **关键参数与判据 + 设计选择与替代方案**：为什么这么选、替代方案为什么落选
6. **验证与消融角色 + 对主 claim 的贡献**：证据在哪、消融中如何被验证

> 来源：math-modeling-agent"必展开槽"（动机→定义→步骤→参数→验证）＋
> writing-systems-papers"每模块 choice → alternatives → why"。

**反向复核（W5）**：对每条 core 机制检查正文是否逐槽展开；与复杂度信号对照
（不只看篇幅）——"小体量高复杂度"机制被一句话带过 → 审计项。

## 2. 术语账本（Terminology Ledger）

**用途**：锁定"源术语（代码/数据/内部口径）→ 论文用词"的映射，禁止写作期同义替换
（回环→工具循环、方案→提案、冗余惩罚→冗余代价 教训）；**图内文字、图注与正文同一账本**。

**生成时点**：W1（与机制注册表同批）。来源 = 代码标识符/配置键/实验日志字段 + narrative + 已有草稿。

**表模板**：

| 源术语 | 论文用词 | 处置 | 锚点/备注 |
|--------|----------|------|-----------|
| 例如 `revision_rounds` | 外部修订轮数 | replace | config.py:42 |
| 例如 "回环" | 工具循环 | replace | 初稿用词 |
| 例如 "保护区" | 保护区 | define_once | 首现定义写入路径 |

- **replace**：正文与图内一律用"论文用词"，源术语原样出现即违规；
- **define_once**：首现处给出定义，之后统一用论文用词；
- **allow**：确需保留的专名（数据格式名、库名、基线名）。

**执行（W2）**：正文、图注、图内文字直接取自本表（**复制不重打**，杜绝手滑漂移）；
Banana Rule 是规则，本表是规则的真源。

## 3. 设计-实现差异台账（Design-Implementation Ledger）

**用途**：凡引用设计文档 / 早期假设的机制声明，必须标注实现状态，
**禁止把"设计里写了"默认写成"已实现"**。

**表模板**：

| 论文/图内声明 | 来源 | 实现状态 | 锚点 | 验证方式 | 处置 |
|---------------|------|----------|------|----------|------|
| 例如"外部修订 ≤1 次" | 设计文档 §3.2 | 未接入 | revision_rounds 无调用点 | code / user / unknown | 删句或降级为"设计为…" |

- **实现状态**：已接入 / 部分接入 / 未接入 / 仅设计。
- **验证方式**：`code`（有 file:line 证据）/ `user`（用户确认）/ `unknown`。
- **硬规则**：`unknown` 不得写成已实现——只能降级措辞（"设计为…"）或标待核；
  W5 逐条核对锚点。图内文字涉及实现状态的，同表管理。

## 4. W5 抽查法（账本 → 审计项映射）

| 账本 | W5 动作 | 检出处置 |
|------|---------|----------|
| 机制注册表 | core 逐槽展开检查 + 复杂度信号对照；未接入机制是否被写成已实现 | 审计项 → 补写/降级措辞 |
| 术语账本 | 扫描正文/图注/图内文字是否出现 replace 原词；define_once 首现定义 | 替换为论文用词 |
| 设计-实现台账 | 逐条核对锚点与状态；unknown 项是否仍以已实现口吻出现 | 降级或补证据 |
| 图中数字 | 图内文字与证据值/caption/正文三方一致 | 见 W5 九类审计第 8 类 |

> 与外部技能的边界：代码级语义审计（假 GT、归一化欺骗）交给 experiment-audit 类工具；
> 证据冻结/漂移交给 evidence-freeze 类工具。**本账本只保证"声明有出处、用词有映射、状态不撒谎"。**
